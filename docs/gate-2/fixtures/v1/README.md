# TrustCapture Gate 2 shared conformance fixtures v1

**Joint-review candidate.** This directory contains the proposed schema and hand-authored outputs for the standalone Kotlin/JVM, Python, and TypeScript PoC. Freeze one exact revision after both sides approve. Evaluators, runners, and production integration are outside this change.

## Files and input boundary

- `workflow.schema.json` defines the valid workflow envelope and expected output shape. `elevator-brakes.json` and `pipeline-measurements.json` use it. `input-rejections.json` is a separate manifest containing literal parser inputs.
- Decode strict UTF-8, with no BOM, duplicate names at any depth, comments, non-finite numbers, unpaired surrogates, trailing commas, or trailing content. Version, rule version, generation, and declared scale integers use integer tokens without fractions or exponents. Generation is positive and at most 2^53−1. Decimal answer tokens are product inputs, so malformed answers remain legal fixture data.
- Identifiers are case-sensitive ASCII matching `[A-Za-z][A-Za-z0-9_-]{0,63}`. No normalization. `fixture_version` is 1 and `profile` is `tc-inspection-semantics-v1`. Each case declares its own capabilities. Rule version 1 and the capabilities `repeat-same-item`, `conditional-photo`, and `fixed-scale-decimal` are in scope.
- Malformed fixture envelopes fail ingestion. Valid envelopes can carry product configuration failures. `package_override` shallowly replaces named parts of the pinned package before product validation. It can contain malformed product content. `published_replacement` is a candidate package for the same-version immutability check. If its form version ID matches the effective package and the definitions differ structurally, return `PUBLISHED_VERSION_CHANGED` with the form version ID. Array order is significant. A different form version is outside this check.
- Structural comparison ignores object key order and compares arrays and strings exactly. Evaluate each independent case without reading `expected`. A runner should process filenames lexically and report the fixture, case ID, and first differing JSON Pointer. The three runtimes consume the same files directly.

## Field and slot semantics

- Store answers as `answers.document` and `answers.items[repeat_id]`. Document targets have a null repeat ID. An item rule can reference the same item and document fields. A document rule cannot reference an item. Repeat IDs and submission order come from the package. Display order is a permutation of pinned IDs and affects presentation only.
- Field types are Boolean, text, enum, and decimal. Fields use `required`; slots use `is_required`. Both default to false. Missing visibility is true and missing conditional requiredness is false. A true static requirement wins over unresolved conditional requiredness. Slots inherit scope and visibility from the parent field, then evaluate their own rules. An inactive or visibility-unresolved parent makes its slot inactive or unresolved respectively. A visible parent with unresolved requiredness does not determine slot state.
- Use typed, single-operator predicates `all`, `any`, `not`, `eq`, `present`, and `is_null`. A field reference is `{scope, field}`. Evaluate field dependencies before slots, with declaration order as the tie-break. Limits are 32 fields, 16 slots, 16 issued items, 64 package predicates, 64 nodes per predicate, depth 8 with root at 1, one to eight children per Boolean group, and 64 receipts per case. Count operator objects as nodes. Reject invalid references, unknown operators, executable definitions, external resource properties, and dependency cycles. Report each cyclic component at its lexically first field ID. No calculations or dynamic repeat membership.
- Use strong three-valued logic. Unresolved survives negation. False makes an `all` false and true makes an `any` true even with unresolved siblings. Otherwise unresolved propagates. Inactive or visibility-unresolved references make `eq`, `present`, and `is_null` unresolved. When visibility is resolved true, those operators can inspect a field whose requiredness is unresolved. On an active reference, `eq` is unresolved for missing, null or invalid operands. `present` checks key existence and `is_null` distinguishes explicit null.
- A missing optional answer is valid. Explicit null is invalid in every active field. False is a valid required Boolean. Active supplied text must contain a character outside ASCII space, tab, LF, VT, FF, and CR. Preserve valid text verbatim. Empty arrays and objects do not coerce to text or Boolean. Enum values are exact IDs. The synthetic pipeline uses `NA` as the ID for N/A.
- Inactive, unresolved, invalid and absent answers are omitted from submission projection and retained in the draft. Emit `UNRESOLVED_CONDITION` on each unresolved target affecting submission. No separate draft mode. Return submission diagnostics for partial drafts while keeping them saveable.

## Decimal answers

Use exactly a string `value`, integer `scale`, and string `unit`. The scale must match the definition and be from 0 to 6. The exact unit ID must match. The ASCII decimal string permits an optional minus sign and an integer part of one to twelve digits, with no leading zero except zero itself. For positive scale require a dot and exactly that many fractional digits. Scale zero has no dot. Reject negative zero, whitespace, exponent notation, plus signs and coercion. Compare valid decimal objects structurally if used in `eq`.

After presence and null checks, emit the first applicable error in this order: `ANSWER_TYPE` for wrong shape or member type, `DECIMAL_SCALE` for a mismatched or out-of-range integer scale, `DECIMAL_UNIT` for a mismatched unit, then `DECIMAL_FORMAT` for lexical failure. JSON integer token spelling also applies to an answer scale at product validation. No numeric comparison or arithmetic.

## Receipt claims and output

- Resolve `for_repeat_item_id` and `for_slot_id` against the pinned package. Document slots require a null claim item and repeat slots require an issued item. The slot’s declared parent supplies the expected field. Match tenant, owner, vendor, visit, assignment, generation, document, field, slot, and repeat ID exactly. A known claim receives diagnostics at the offered slot. An unknown claim emits an unmatched target mismatch and still participates in identity-conflict detection.
- Keep every supplied receipt in input order. For evaluation only collapse identical records for the same claim and receipt ID. Conflicting reuse of a receipt or evidence ID invalidates all participating candidates, including inactive ones. Multiple distinct eligible exact candidates on one active slot conflict as well. Per known candidate emit at most one primary error in order: conflict, target mismatch, then ineligibility. An exact nonconflicting receipt on an inactive slot emits no eligibility diagnostic and contributes no binding. Neither inactive nor unresolved slots produce bindings. A required active slot still unsatisfied emits missing evidence after the receipt diagnostics.
- Output applicability and projection in document scope then pinned repeat order, with fields before slots and declaration order within each group. Project every repeat even when it has no valid active answers. Bindings carry the full recorded target and receipt/evidence IDs. They exclude the claim and eligibility flag.
- Configuration errors carry `code` and `subject_id`, with null first when sorting. Field and slot diagnostics carry `document_instance_id`, `repeat_item_id`, `field_id`, `slot_id`, and `receipt_id` in addition to `code`. Set unused IDs to null. Slot errors have null `field_id`. Unmatched receipt errors have null target IDs.
- Sort configuration errors by code then subject. Sort ordinary errors by document scope, pinned repeat order, field before slot, and declaration order. For the same slot put receipt rejection before missing evidence, then use code and receipt ID within each phase. Sort unmatched receipt errors last by code and receipt ID. Null sorts first. Collapse exact duplicate error objects.
- `can_submit` is true only when both error arrays are empty. Configuration rejection returns empty applicability, bindings, ordinary errors, and projection. Always return `retained_answers` and `retained_receipts` unchanged. The backend still owns authorization, receipt eligibility and acceptance.

## Standalone parser rejection checks

The companion manifest keeps malformed literal JSON separate from valid workflow inputs. Decode one value per entry. A missing expected code is represented by JSON null for successful validation.

| Check | Validation boundary |
| --- | --- |
| `json` | Decode strict JSON only. Duplicate nodes yield `DUPLICATE_KEY`; other invalid syntax or invalid Unicode yields `INVALID_JSON`. |
| `fixture_header` | Require an object, reject unrecognized supplied top-level keys first, require version and profile, check integer token and profile string type, then check the supported pair. No full-envelope requirements here. |
| `identifier` | Decode a standalone value and require a string matching the ASCII identifier grammar. Other values yield `INVALID_ID`. |
| `capabilities` | Decode a standalone array of identifier strings and reject duplicate values with `DUPLICATE_CAPABILITY`. This check does not compare against package requirements. |
