# TrustCapture Gate 2 shared fixture contract v1

**Proposed freeze candidate.** The shared repository owns this directory. WSL and Android must approve these exact files and expected outputs before Kotlin, Python, or TypeScript implements an evaluator. The two workflows use synthetic data. They do not encode customer forms or regulatory thresholds.

## Input and versioning

- Accept one UTF-8 JSON object with no BOM, comments, trailing commas, duplicate member names, non-finite numbers, or unpaired surrogates. Reject duplicates at every depth before converting JSON objects to native maps. Reject unknown properties outside answer maps and explicitly extensible metadata. In v1 there is no extensible metadata. Preserve strings exactly. Object order has no meaning. Array order does.
- Each file declares `fixture_version: 1` and `profile: "trustcapture-gate2-v1"`. Unknown versions or profiles fail with `UNSUPPORTED_VERSION`. A capability is an exact case-sensitive ID. `client_capabilities` is an unordered set with unique entries. Every `package.required_capabilities` entry must be supported before evaluation. Missing capabilities yield `UNSUPPORTED_CAPABILITY`.
- Fixture, case, field, slot, and capability IDs match `[a-z][a-z0-9_-]{0,63}`. Visit, assignment, document, form version, repeat, receipt, and evidence IDs use canonical lowercase hyphenated UUID strings. IDs cannot alias by normalization. A repeat item ID is server-issued and unique within the pinned document. The assignment generation is a positive integer of at most 2^53−1. Require JSON integer syntax for version, generation and scale. Reject unknown or duplicate members of the display order. The display order must be a permutation of the pinned repeat list.
- Each case declares `mode` (`draft` or `submit`), `display_order`, `answers`, `receipts`, and `expected`. Optional `client_capabilities` replaces the file defaults. Optional `package_override` replaces the entire named top-level package member in a case, with no recursive merging. It is a fixture-only input for schema rejection tests.
- The outer keys are `fixture_version`, `profile`, `fixture_id`, `client_capabilities`, `package`, and `cases`. The package contains visit, assignment, generation, document and form-version IDs; required capabilities; `repeat_items`; ordered `fields`, `document_fields`, and `slots`. Answer containers are keyed by repeat UUID then field ID, with `document_answers` as a separate field map. This v1 fixture output supports repeated fields only. `document_fields` and `document_answers` are reserved empty containers until document-level output is specified. Reject references to undeclared document fields.
- Field definitions contain `id`, `type` (`text`, `boolean`, `decimal`, `select`), and optional `required`, `visible_if`, and `required_if`. Decimal fields require `scale` and `unit`; select fields require unique string `options`. An unspecified visibility condition is true. An unspecified `required` is false. If both requiredness forms are present, static true wins. Slots contain `id`, `field_id`, and `required_if`. Field and slot IDs share a namespace.

## Rules and values

- Answer lookup distinguishes absent, explicit null, false, empty string, empty array and empty object. Type validation runs on active fields only. Required Boolean false is valid. Empty text means zero characters or only ASCII space, tab, CR, or LF. Preserve text verbatim. In v1 null is invalid for active fields. An empty string is valid for optional text but fails active required text. Empty arrays and objects are type errors for text, Boolean and select. Decimal objects have their own shape check.
- Predicates are single-operator objects. Operators are `eq`, `present`, `is_null`, `not`, `all`, and `any`. `eq` takes exactly one typed reference and one scalar literal. `present` tests whether the key exists, including a null answer. `is_null` is true only for explicit null. Reference scope `item` is the same repeat. Scope `document` addresses declared document fields in `document_answers`. Neither scope can reference another repeat or a calculated value. The two files exercise only item scope.
- Validate all rule references, operator arity and literal compatibility before evaluation. Limit predicate depth to 8 and each Boolean group to 1–16 children. Reject self references and cycles in field visibility and requiredness dependencies. Slot rules can depend on fields. Fields cannot depend on slots. Reject invalid references with `INVALID_FIELD_REFERENCE` at the referencing field or slot, cycles with `RULE_CYCLE` at the lexicographically first ID in each cyclic component, and malformed or out-of-bounds nodes with `INVALID_PREDICATE`. Advanced calculations and cross-repeat aggregation are outside v1.
- `eq` on an absent, null, invalid, or inactive value is unresolved. An inactive reference behaves as absent for presence and null tests. `not(unresolved)` is unresolved. `all` short-circuits to false if any child is false and `any` to true if any child is true. Otherwise unresolved propagates. A false visibility condition makes the field inactive. An unresolved visibility or requiredness condition marks the target unresolved. An active, resolved target is required or optional. Slots without an explicit visibility rule use their required condition for applicability in v1, so false makes them inactive.
- Retain the original answer map, including hidden and invalid values. Project valid, active answers only, with one entry for every pinned repeat even when its answer object is empty. Exclude inactive and unresolved receipts from evidence bindings. Draft mode omits completion errors for missing, empty-required, unresolved and missing required evidence, while retaining type and receipt errors. Submit mode emits all applicable errors. `can_submit` is false in draft mode and is true in submit mode only with zero errors. A projection can be returned for diagnostics even when submission is blocked.

## Measurement format

- A decimal answer is exactly `{"value":"2.50","scale":2,"unit":"mm"}`. Required keys have JSON string, integer, and string types respectively. Reject extra keys. The scale is from 0 to 18 inclusive and must equal the field definition. Unit comparison is exact and case-sensitive against the pinned unit ID. The value is ASCII `-?(0|[1-9][0-9]*)` followed, for positive scale only, by a dot and exactly that many digits. Maximum total value length is 80. Reject negative zero, exponent syntax, leading plus sign and leading zeros. Do not parse floating point or silently convert units. This profile validates representation and unit only. Ranges and comparisons between decimal fields require a future capability.
- Error precedence per active answer is missing, null, top-level type, decimal object shape or scale, decimal format, then unit. Emit at most one answer error per field. Select values are stable enum IDs.

## Evidence and output

- Check exact visit, assignment, generation, document, field, slot and repeat identity, and require an eligible receipt. A wrong target emits `EVIDENCE_TARGET_MISMATCH` at the intended active slot and does not satisfy it. An eligible receipt for a hidden slot is retained as input but omitted from output bindings. An exact ineligible receipt emits `EVIDENCE_INELIGIBLE`. Reusing a receipt ID or evidence ID, or attaching multiple candidate receipts to a one-photo slot, emits `EVIDENCE_DUPLICATE` and none of those candidates satisfies that slot. Emit `REQUIRED_EVIDENCE_MISSING` in submit mode if the slot remains unsatisfied.
- Receipt cases supply `for_item` and `for_slot` as the claimed local binding, distinct from the receipt’s recorded target. Use the claim to locate the error. Validate claim IDs before considering eligibility. Unknown claims are malformed input. A canonical submission projects answers and bindings in server-issued repeat order, independent of display order. Within each item, fields and slots follow package declaration order.
- Expected output contains `configuration_errors`, `applicability`, `retained_answers`, `submission_projection`, `evidence_bindings`, `errors`, and `can_submit`. Error objects use `code` and `target_id` for configuration errors. Answer and evidence errors add `repeat_item_id`, with `target_id` identifying the field or slot. A containing fixture has exactly one document, so the document ID is available from the package. Runtime adapters can include it in API errors.
- For deterministic errors, visit items in pinned order, then fields in declaration order, then slots in declaration order. Emit dependency errors at the affected target. For a slot, an evidence rejection precedes missing evidence. Configuration errors sort by code then target ID. After configuration rejection, return the input answer map unchanged, empty applicability and projections, zero ordinary errors, and `can_submit: false`.
- The runner exits successfully only when structural JSON equality matches every expected result. It reports the fixture, case, and first differing JSON Pointer on mismatch. Compare object keys independent of order, array order exactly, and strings literally. `input-rejections.json` is a companion manifest of literal JSON inputs for parser and field checks, so malformed values survive the outer fixture parser. Run one named parser or validation check per entry before running the two workflow files.

## Named rejection checks

The `check` field selects the boundary being tested. Decode exactly one JSON value from `input` with the strict syntax and duplicate-key rules above. Keep the original number token available for integer checks. Apply the workflow envelope requirements only when reading a full workflow file.

| Check | Validation order and scope |
| --- | --- |
| `json` | Run strict JSON decoding only. Check for duplicate names at every object depth and return `DUPLICATE_KEY` for a duplicate. Other invalid JSON, including non-finite literals or unpaired surrogates, returns `INVALID_JSON`. |
| `fixture_header` | Require an object (`INVALID_TYPE` otherwise). First reject supplied keys outside the workflow fixture's top-level allowlist with `UNKNOWN_PROPERTY`. Next require `fixture_version` and `profile` (missing gives `MISSING_PROPERTY`). Check the version token for JSON integer syntax (`INVALID_INTEGER` otherwise), then require a string profile (`INVALID_TYPE` otherwise). Finally compare version and profile to the supported pair (`UNSUPPORTED_VERSION` for an unknown pair). Do not require the remaining workflow members or validate their contents in this check. |
| `uuid` | Decode a standalone JSON value. Require a string in canonical lowercase hyphenated UUID form. Return `INVALID_ID` for any other type or spelling. |
| `capabilities` | Decode a standalone JSON value. Require an array (`INVALID_TYPE` otherwise), then validate each element against the capability-ID grammar (`INVALID_ID` for a type or spelling violation). Then reject duplicate IDs with `DUPLICATE_CAPABILITY`. This check does not compare the list to package requirements. |
