# TrustCapture Gate 2 Android architecture assessment

## Recommendation

Use **native Compose with a small versioned portable form and rule format** for the first Gate 2 pilot. Keep camera, signing, durable drafts, evidence identity, and the upload outbox native. Let Android and React evaluate the same declarative rules for feedback. Let Python independently enforce the same contract at acceptance. Preserve an adapter boundary so that a bundled hybrid renderer can be tested if the required form breadth or authoring workflow makes it worthwhile.

Gate 2 depends on the Gate 1 identity and durability contract. The checkout has a working integration slice and useful local checks. It has yet to demonstrate a forms-capable signed upgrade or end-to-end evidence recovery on a device.

## Renderer alternatives

Effort is incremental Android engineering for a staging-quality Gate 2 slice **after** Gate 1 integration stabilizes. It assumes one engineer, an agreed schema, two synthetic workflows, and existing backend and web counterparts. It excludes an authoring product, customer rollout, and regulatory validation. Performance and accessibility are hypotheses until measured on devices.

| Rank and option | Offline, UX and performance | Parity, security and delivery | Estimate |
| --- | --- | --- | --- |
| **1. Native Compose + portable JSON** | Cached form can start in airplane mode with native text input, TalkBack semantics, and a single task flow. Use lazy repeat rendering. Measure focus, font scaling and edit latency with larger forms. | Reuses the renderer, Room and camera boundaries. Schema versions and capability flags permit data-only rollout within supported controls. Native UI and typed-rule adapters need upkeep alongside React. No browser bridge. | **4–7 engineer-weeks** |
| **2. Hybrid bundled web form + native workflow** | Bundled JS, CSS and assets support offline startup. More startup and memory paths to measure, including WebView process recreation and IME/TalkBack focus through camera return. | Can reuse React rendering, or a pinned SurveyJS renderer behind an adapter. Native owns persisted answers, trusted camera, keys, queue and authorization. Synchronize a small versioned message schema and benchmark the bridge. React reuse can pay off if forms are wide and already shared. | **5–8 engineer-weeks** |
| **3. Bundled WebView-led SurveyJS or equivalent** | Broad built-in controls and dynamic panels. Offline only if the whole renderer, assets and required data are local. Browser draft storage creates a second recovery lifecycle. | Faster rendering demo, larger production integration. SurveyJS has its own visibility, requiredness, dynamic panel, and hidden-value behavior. Need explicit adapter/engine pinning, schema compatibility and a secure native evidence handoff. Browser-only evidence does not satisfy the trusted capture contract. | **5–9 engineer-weeks** |
| **4. ODK interoperability** | Collect offers mature offline forms, repeats, photo widgets and draft recovery. Separate app UX, with a different form lifecycle and transfer path. Test modest devices for complex XPath/repeats. | Viable if customers already author XLSForms or want import/export. An import adapter can whitelist supported capabilities. Ordinary Collect camera and submission do not produce the Gate 1 authorized reservation and receipt. An adapter or customized client would need stable IDs and native trust integration. | **2–4 weeks for import feasibility; 8–12+ weeks for a credible trusted-capture client slice** |

WebView design for either web option: bundle versioned assets with the APK and load them from an app-local HTTPS origin such as `https://appassets.androidplatform.net/assets/` via AndroidX `WebViewAssetLoader`. No CDN, remote fonts, analytics, page navigation, arbitrary code in schemas or direct network requirement for offline startup. Block unexpected origins and resource loads. Disable file and content access where unnecessary. Use origin-restricted structured messages with explicit size and capability limits. JavaScript can request a draft edit or capture using stable IDs. Native verifies the exact active document and slot against its package before accepting the request. Keep credentials, file paths, key operations, network operations, and acceptance authority outside the bridge. Never derive a target from DOM position or a dynamic panel index. [Android local assets](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content) · [Android bridge security](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)

SurveyJS documents conditional expressions and per-panel scope, including configurable clearing of hidden values. ODK documents grouped repeats, positional references and offline form recovery. These are reasons to test adapters and semantic equivalence, not evidence of compatible TrustCapture identities. [SurveyJS logic](https://surveyjs.io/form-library/documentation/design-survey/conditional-logic) · [SurveyJS dynamic panels](https://surveyjs.io/form-library/examples/how-to-use-expressions-in-dynamic-panel/documentation) · [SurveyJS hidden-value setting](https://surveyjs.io/form-library/documentation/api-reference/question) · [ODK repeats](https://docs.getodk.org/form-repeats/) · [ODK recovery and offline editing](https://docs.getodk.org/collect-filling-forms/)

## Rules and representation

| Approach | Assessment |
| --- | --- |
| Vendor-native semantics | Convenient when rendering and authoring share that engine. Pin engine and schema together and review the supported operator subset. Python still needs independent authoritative evaluation or a deliberate server runtime decision. Test coercion, truthiness, hidden clearing, panel scope and engine upgrade differences. |
| Small TrustCapture format | **Preferred.** Version a typed predicate tree with explicit field IDs, scope, `all`, `any`, `not`, presence, equality and typed comparison. Let publication validate references, types and depth. Kotlin, TypeScript and Python can implement a small evaluator against identical fixtures. The web authoring tool can generate this format without exposing arbitrary expressions. |
| JSON Schema validation profile + portable predicates | Strong complementary choice for static shapes, enum and presence checks. Pin a dialect and supported keywords. JSON Schema conditionals can validate instances. UI layout, hidden-answer policy, repeat identity, and evidence applicability still need explicit metadata and predicate semantics. Prototype validator parity and document format and decimal-string limits before adopting. [JSON Schema conditional validation](https://json-schema.org/understanding-json-schema/reference/conditionals) |

Proposed initial semantics for review:

- Treat **missing**, explicit **null**, Boolean **false**, and empty string/list as distinct. Required means present and valid for that field type, so false is a valid Boolean answer. Use explicit predicates for presence and empty values. Publish a whitespace policy per text type. No implicit conversion between text, numbers, Booleans or null. Define unknown predicate results separately from false so a missing answer cannot satisfy a negated comparison. Block submission when a required applicability decision is unresolved.
- Scope references explicitly to **this repeat item** or **the document**. Reject implicit sibling lookup. Allow nested Boolean groups with bounded depth. Cross-repeat aggregation and dynamic repeat membership require a separate capability. Keep signable evidence targets keyed by ID.
- Keep hidden answered fields in the account-scoped local draft to support undo. The recommended submitted answer projection omits inactive fields and excludes their evidence from required-slot satisfaction. Agree the exact projection with Python and preserve the accepted snapshot. Current Gate 1 validators do not implement this dynamic rule set.
- Use exact decimal strings with declared unit and scale, plus explicit comparison and rounding rules when needed. Date-only values and instants are distinct. Specify timezone where calendar or deadline semantics depend on it. Avoid evaluator use of device wall time for authoritative eligibility.
- Separate cross-field validation from derived calculations. Start with declarative comparisons. Evaluate calculations later with typed inputs, dependency sorting, cycle rejection, versioned rounding and server recomputation. Reject unknown operators, missing references and cyclic calculation dependencies at publication.
- Share schema, rule trees and independent golden fixtures across Kotlin, React/TypeScript and Python. A renderer adapter may share TypeScript between web and a bundled web option. A shared executable across all three would require a distinct runtime decision and offline and package-size evaluation. Golden vectors should include nested groups, repeat scoping, missing/null/false/empty, retained hidden values, decimal boundaries, dates, and mismatches between local hints and server acceptance. Published forms carry a capability set, schema version and rule version pinned to each document. Older clients preserve drafts and block submission when required capabilities are unsupported.

## Evidence identity and lifecycle

Reuse the backend-owned immutable workflow/form/document pin. For two synthetic brake items, use stable server-issued IDs `A` and `B` in the draft model and target resolver. Bind the second photo to `B` with the exact tenant, owner client, visit, assignment ID and generation, document instance, field, and slot. The UI can display `B` first without changing its binding. Preserve the pinned submission order where the Gate 1 validator requires it. Gate 1 currently pins repeat membership. Gate 2 deletion, addition and undo need a reviewed membership protocol before enabling them. A proposed local delete tombstones the item and disables its slot, retaining the bound media according to policy. Undo restores the same item ID if still authorized. A replacement item gets a fresh identity and cannot inherit the old photo.

Before first network I/O, durably record the account, exact assignment and target, local capture ID, idempotency key, canonical media path, byte length, SHA-256, capture time, signing-key reference and server key ID. Persist signed metadata and stable request inputs. Stage the file and commit the local target and outbox binding before enqueue. Reconcile an orphan file after interruption without inferring a missing binding. Persist the server reservation once known, and stage transitions and immutable finalization request before dispatch.

On restart, resume the persisted phase using the same stable key and bytes when the backend authorizes exact replay. A lost response after commit must recover the existing receipt and evidence ID. Compare the exact target and eligibility, and durably commit acknowledgement and binding before allowing cleanup. Retain files on failure or uncertainty under the retention policy. Separate evidence work from form submission. Reassignment away and back increments the generation. The original photo stays on the old generation. Compatible answers can transfer deliberately to a replacement draft, while required evidence must qualify for the new exact target. Device rules and cache are advisory. The backend reauthorizes the operation and verifies receipt deadline and key eligibility.

For the synthetic pipeline form, collect an exact measurement such as `{"value":"2.50","scale":2,"unit":"mm"}` with a separate enumerated inspection result of PASS, FAIL or N/A. Define a synthetic rule making severity and a photo required for FAIL within the same repeat. Define N/A as its own option, with an explanation if product requires one. Changing FAIL to PASS can hide the severity and photo slot without deleting the local values or satisfying another slot. No engineering or regulatory threshold is assumed.

| Scenario | Observable pass evidence |
| --- | --- |

| Force-stop and reboot | Interrupt after a durable draft save, between file save and queue commit, and with work pending. Reopen and compare answer keys and hashes. | Signed v15 upgrade | On a dedicated phone, use Play-signed v15 / Room v10 and a signer-compatible successor. | Revocation, reassignment, and restored access | Obtain a denial with pending media, retain answers in the same account, and prevent automatic reuse. Reassign away and back and read a new generation. A prior capture stays bound to the old target. Restore eligible work only after checking the exact assignment and receipt. |
| Republished schema | Publish a successor while an older document is pinned. Old draft opens and submits against its old pin if still authorized. New assignments use the new pin. Unknown required capability blocks submission while retaining draft data. |
| Hidden answers and partial repeats | Fill severity and a photo, toggle the controlling result and restart. Restore the retained local values when shown again. ## PoCs and decisions that could change the ranking

1. **Rule parity.** Run a shared truth-table fixture in Kotlin, TypeScript and Python for the two synthetic forms. Require identical applicability, error IDs and answer projection; include invalid and unsupported schemas.
2. **Renderer shoot-out.** On a supported lower-memory device and a current device, measure airplane-mode cold start, edit latency and memory with a realistic repeated form. Exercise TalkBack, large text, keyboard, camera return and force-stop. Compare Compose with one fully bundled hybrid prototype. Favor hybrid if it materially reduces duplicated renderer effort while meeting the same device and recovery criteria.
3. **Evidence identity and durability.** Prove stable target IDs through reorder, tombstone and undo with native capture and staging replay. Run the Gate 1 signed upgrade independently before assuming the same storage lifecycle for Gate 2.
4. **Interoperability trigger.** Pursue ODK/XLSForm import only when the pilot has substantial existing forms. Test a whitelist import with repeats and relevance rules and report unsupported semantics and evidence mapping cost.

**Questions for WSL:** What is the published schema and rule version lifecycle? Who allocates dynamic repeat IDs, and how are ordering, tombstones and membership revisions represented? What are the hidden-answer submission projection and sealed snapshot rules? Which stable validation and access error codes apply to stale packages and unsupported capabilities? Confirm idempotency lifetime, media retention, assignment generation and exact receipt eligibility/read-back for Gate 2.

**Product decisions:** Required pilot controls and form sizes, visibility/retention policy for hidden and deleted answers, whether users can add or reorder repeats, allowed decimal units and locale display conventions, and whether the pilot needs XLSForm import or complex calculations. Agree supported client capabilities before allowing a form to be assigned.

**Confidence:** High for the source inventory and current wiring boundaries. Moderate for the ranked recommendation under the stated scope. Effort, real-device performance, accessibility, SQLCipher migration, backend parity and replay are unverified until the listed tests run. Gate 1 device acceptance remains independent of this research and production stays on hold.
